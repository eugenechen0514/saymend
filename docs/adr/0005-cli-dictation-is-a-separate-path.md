# CLI 聽寫走獨立的一條路，結果只回給呼叫端

Claude Code 的 mod 要把 Saymend 當語音輸入來源，組成「說話 → 文字送進 Claude Code → 回覆用 `say` 唸出來」的迴圈。mod 透過 `saymend` CLI 請執行中的 app 錄一段話（契約見 `docs/control-interface.md`）。這段話的文字必須**只回給呼叫端**：mod 自己會把它送進 Claude Code，若同時上屏，文字會被打兩次。

決定：CLI 聽寫由新的 `CLIDictationController` 負責，**與熱鍵聽寫的 `DictationController` 完全分開**。它直接串接麥克風與辨識引擎，結果經本機確定性後處理（簡轉繁、詞彙表誤轉寫）回給呼叫端；`--polish` 才走語言模型。這條路上沒有 inserter、沒有剪貼簿、沒有帳本／延續窗／口頭修正。熱鍵那一側只多兩個掛點：`activity`（給 `status`／`events`）與 `yieldForExternalCapture()`（開麥前確認熱鍵聽寫沒在用麥克風）。麥克風、辨識引擎、HUD 共用同一組實例，兩者互斥。

## Considered Options

**在 `DictationController` 加一個「不上屏」模式。** 看似改動最小，實際最深：上屏散在十幾條落地路徑上（raw 定稿、緩衝句、潤飾替換、過期尾端回收、修正、復原、救援），每一條都要加「CLI 模式就不寫」的分支，漏一條就是文字被打進前景 App；帳本、凍結、延續窗、密碼欄閘門的語意也都得重新定義成「沒有欄位時怎麼辦」。否決：把一個 1800 行、已被幾十張 issue 磨出來的狀態機拿來承載一個不需要它任何一項機制的用途。

**CLI 自己錄音、自己載模型。** 否決：本機 WhisperKit 的模型一顆數百 MB 到 3 GB，兩個行程各載一份；麥克風授權（TCC）也得另外給 CLI；而且 app 就無從知道麥克風正被誰使用，熱鍵聽寫與 CLI 聽寫會搶同一支麥克風。

## 交給實作者決定的兩點

**CLI 聽寫中按熱鍵或 Esc。** CLI 聽寫在畫面上的樣子就是一段「鎖定聽寫」（不必按住熱鍵也在錄），所以沿用鎖定聽寫的操作：錄音中點熱鍵＝結束並定稿（文字交給等待中的 `dictate`）；Esc＝取消並丟棄（`dictate` exit 5），Esc 照樣被吞掉、不傳給前景 App。辨識／潤飾中按熱鍵只提示、不開始熱鍵聽寫（辨識引擎還在處理這一段）。熱鍵**不**用來「取消 CLI、改開熱鍵聽寫」：那會讓使用者以為的「說完了」變成「白說了」。代價：免手動迴圈正在等使用者開口時，前景 App 收不到 Esc（例如 Claude Code 的中斷鍵）；按下去的效果是取消這次等待（mod 收到 exit 5），而不是傳給 Claude Code。

**密碼欄位規則（規格 §5.3）不適用。** §5.3 的觸發條件是「聽寫的目標是聚焦中的密碼欄」——拒絕的理由是文字會被打進那個欄位。CLI 聽寫沒有目標欄位，結果在構造上到不了任何欄位，焦點在哪裡與使用者的話要去哪裡無關。套用它只會讓免手動迴圈在焦點剛好停在某個密碼欄時隨機失敗，換不到任何保護。§5.3 對熱鍵聽寫的行為完全不變。

## Consequences

- 熱鍵聽寫、口頭修正、密碼欄位硬規則的行為不變；既有測試零改動。
- 熱鍵聽寫結束後的 8 秒延續窗中開始 CLI 聽寫：延續窗被封存（同使用者活動）。不封存的話，延續窗到期時發的 `.hidden` 會把 CLI 錄音中的 HUD 一起收掉——錄音就變成看不見。延續窗裡若還有潤飾在途，`dictate` 回忙碌（exit 4），不封存。
- 詞彙表的誤轉寫第一次被用來做確定性替換，但只在 CLI 這條路上；熱鍵聽寫仍只把它放進提示詞與辨識偏置。
- 端點判斷（`--silence-ms`）以音量位準為主、辨識文字變長為輔，門檻隨環境噪音浮動。數值（下限 0.08、底線 × 2.5、開口需 0.25 秒）是憑經驗訂的；除了合成語音的 harness，也已在一支外接耳機麥克風上由真人實測 10 段（全部靜音自動結束，見 `docs/control-interface.md` 的驗證紀錄）。這支麥克風的環境噪音底線約 0.07～0.11，已高於固定下限 0.08——沒有自適應的話環境音會被誤判成開口。其他麥克風與環境的位準分布仍待累積；每段 CLI 聽寫結束時 log 會記位準摘要，供日後校準。
- 沒有內容的 CLI 聽寫不開歷史 session：免手動迴圈會反覆「沒人說話就放棄」，熱鍵聽寫那種「按一下就開一筆」的做法會把歷史洗掉。
