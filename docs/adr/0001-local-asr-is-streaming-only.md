# 本機語音辨識只提供串流，不保留批次模式

本機辨識原本是批次的：收完整段音訊才一次辨識。這使得一個聽寫階段只會產生一個話語，而 Saymend 的核心賣點——口頭修正已上屏文字、以及回收晚到的潤飾——**都以「一個階段內有多個話語」為前提**，因此離線使用者拿到的是一個功能殘缺的版本。我們決定把本機引擎整個換成串流，不保留批次路徑，讓離線與線上享有同一組機制。

## Considered Options

**兩種並存，讓使用者自己選。** 否決：測試矩陣加倍，而本專案對每條路徑都要求變異驗證；更根本的是，「批次」對使用者而言不是一個功能選項，而是一個會讓其他功能悄悄消失的陷阱——設定頁無法誠實地把這件事解釋清楚。

**預設串流、進階設定留回退開關。** 否決：仍然要長期維護兩條路徑，只是把複雜度藏起來。真要退回，`git revert` 比養著一條沒人走的路便宜。

**批次的真實優點也一併放棄了**：它一次看到整段音訊，上下文完整，斷句與標點可能較好；串流是滑動視窗重複解碼，CPU 與耗電都較高。我們判斷「功能完整」的價值高於這兩項。

## Consequences

- 取消聽寫的意義改變：批次時取消等於「本來就沒有文字上屏」，串流之後文字已經在螢幕上，取消變成退掉它。與系統內建引擎的行為一致。
- 原本 10 分鐘的錄音長度上限隨之取消——那是批次累積整段音訊的包袱，不是產品選擇。
- 大模型在較慢的機器上可能跟不上即時。我們刻意不預先設計對策，先量測再決定是否需要。
